# 만월체크 재구매 알림 모델 · 전달 안내

> 읽는 분: 만월체크 앱 개발자. 머신러닝 배경 없이 읽을 수 있게 썼습니다.
> 문서 4개 + 실행 파일. 순서대로 읽으면 됩니다.

| 파일 | 내용 |
|---|---|
| `README.md` (이 문서) | 모델이 뭘 하는지, 앱에 어떻게 붙는지 |
| `SCHEMA.md` | 앱이 읽을 표 1개, 앱이 써줄 이벤트 6개, 앱이 꼭 지킬 규칙 3개 |
| `RUNTIME.md` | 실행 환경(Cloud Run Job), 권한, 하루 일정, 장애 시 |
| `QUESTIONS.md` | 시작 전에 답이 필요한 질문 |
| `Dockerfile`, `run_daily.py`, `requirements.txt` | 매일 1회 도는 배치 (빌드는 우리가, 실행은 `RUNTIME.md`) |

---

## 1. 한 줄 요약

**카페 사장님이 어떤 물건을 언제 다시 살지 예측해서, 그 7일 전 아침에 앱이 알림(또는 장바구니 담기)을 띄우게 하는 것.**

모델은 사장님 대신 주문하지 않습니다. "이 물건 슬슬 떨어질 때 됐어요"를 미리 알려주는 역할입니다.

## 2. 앱 입장에서 보면

```
매일 새벽 (예: 06:00)
  배치가 돌아서 "오늘 알림 보낼 것" 목록을 표 하나에 써 둠
        ↓
앱 서버
  표에서 status = 'due' 인 행을 읽음
  → 해당 매장에 알림 / 장바구니 담기
  → 사장님이 지우거나 수량 바꾸거나 결제하면 그 행동을 이벤트로 기록
```

앱이 모델을 직접 부르는 일은 없습니다. **표를 읽고, 이벤트를 쓰는 것**이 전부입니다.

## 3. 모델은 안에서 뭘 하나 (몰라도 되지만 궁금하면)

매장 × 품목 짝마다, 마지막으로 산 날을 기준으로 이렇게 계산합니다.

| 단계 | 하는 일 | 예 |
|---|---|---|
| ① 다음 구매까지 며칠? | 그 품목을 **몇 번째** 사는지에 따라 다르게 | 1번째: 그 품목을 다른 매장들이 보통 며칠 만에 다시 사는지(중앙값). 2번째: 직전에 산 간격 그대로. 3번째부터: 학습된 모델(XGBoost)이 이 매장의 구매 습관(직전 간격, 평균 간격, 수량 흐름 등 21개 숫자)으로 예측 |
| ② 며칠 앞당길까 | 늦는 것보다 조금 이른 게 낫다는 판단. 셋 다 **앞당기기만** 함 | 예측 간격의 30%(7~14일) 여유. 매장 전체 주문 리듬이 더 이르면 그쪽으로 최대 7일. 과거에 알림보다 먼저 사 버린 매장은 그 부족분만큼 다음부터 더 일찍(최대 21일) |
| ③ 알림 시각 | 보정된 예측일의 **7일 전 아침 9시** | 10/15 예측 → 10/8 09:00 알림 |
| ④ 수량 | 매장 리듬 값이 있으면 그것, 없으면 모델 예측 | 보통 직전 수량 근처 |

모델은 **하나**(XGBoost)이고 나머지는 전부 단순 규칙입니다. 딥러닝·GPU 없습니다.

## 4. 얼마나 맞나 (솔직한 숫자)

과거 데이터를 재생한 결과입니다. 실제 앱에 붙이면 사장님 행동이 달라지므로 **다시 재야 합니다.**

- 알림 후 21일 안에 실제로 다시 산 비율: 약 62%
- 알림보다 먼저 사 버린 경우(늦은 알림): 약 9%
- 매장 유형별로 차이 큼. 표의 `customer_group` 열로 구분 가능

| `customer_group` | 뜻 | 대략 적중 |
|---|---|---|
| `stable` | 주기가 일정한 매장 | 80%대 |
| `irregular`, `rebound`, `speeding_up`, `slowing_down` | 주기가 흔들리는 매장 | 50%대 |
| `insufficient` | 아직 2~4번밖에 안 산 짝 | 50%대 |

앱에서 `stable`은 "예상 재구매일", 나머지는 "참고" 정도로 톤을 나눠 보여주는 것을 권합니다.

**첫 구매 품목 알림**은 5건 중 4건이 90일 안에 재구매로 이어지지 않았습니다. 그래도 넣기로 했고, 앱의 삭제 로그로 실제 비용을 재서 유지 여부를 정합니다. 그래서 이벤트 기록이 중요합니다.

## 5. 앱이 꼭 지켜야 하는 3가지

1. **같은 `suggestion_key`는 한 번만 담는다.** 배치는 매일 다시 도니까 같은 제안이 매일 표에 나옵니다. 이미 처리한 키는 건너뜁니다.
2. **사장님이 지우거나 수량을 바꾼 제안은 다시 덮어쓰지 않는다.** 앱이 수락/수정/거절 상태를 기억해야 합니다.
3. **`ab_group = 'holdout'` 매장에는 아무것도 보내지 않는다.** 아래 6번 참고.

## 6. A/B 그룹과 홀드아웃이 왜 필요한가

표의 `ab_group` 열에 매장마다 `control` / `treatment` / `holdout` 중 하나가 적혀 있습니다. 매장ID를 해시해서 정하므로 항상 같은 값입니다.

- **holdout (약 5%)**: 알림을 **끝까지 안 보내는** 매장. "알림이 없으면 원래 언제 사는지"를 계속 알려주는 기준선입니다. 이게 없으면 모델이 자기가 앞당긴 구매를 보고 "내 예측이 맞았네" 하고 배우는 자기확증이 생깁니다.
- **control / treatment**: 나중에 규칙을 바꿀 때 절반씩 다른 규칙을 돌려 비교하는 용도. 처음엔 둘 다 같은 규칙입니다.

연동 **시작 시점부터** 있어야 합니다. 나중에 붙이면 이미 알림에 익숙해진 매장이 섞여 비교가 오염됩니다.

## 7. 앱이 써줘야 하는 이벤트 (요약)

자세한 필드는 `SCHEMA.md`. 이유만 적습니다.

| 이벤트 | 왜 필요한가 |
|---|---|
| `cart_suggested` | 우리가 실제로 뭘 보냈는지 기준점 |
| `cart_item_removed` | **가장 중요.** 너무 일찍 보낸 비용의 유일한 증거 |
| `cart_quantity_edited` | 수량 예측이 얼마나 틀렸는지 |
| `cart_checkout` (품목별 "우리 제안 / 직접 담음" 표시) | 주문 DB만으로는 우리 제안이었는지 알 수 없음 |
| `cart_item_added_manually` | 우리가 놓친 품목 |
| `cart_viewed` | 장바구니에 몇 개 쌓이면 안 보는지 |

## 8. 우리가 하는 것 / 앱이 하는 것

| 우리(모델 쪽) | 앱(만월체크 쪽) |
|---|---|
| Docker 이미지 제공, 버전 올릴 때 새 이미지 전달 | 매일 1회 배치 실행(Cloud Run Job) 또는 우리에게 권한 부여 |
| 제안 표 스키마 유지 | 표 읽어 알림/담기 |
| 이벤트 표를 읽어 성능 측정, 규칙 개선 | 이벤트 6종 기록 |
| 배치 실패 시 원인 대응 | 실패 알림을 우리에게 전달 |

## 9. 지금 안 하는 것

- 자동 주문·자동 결제. 제안만 합니다.
- 실시간 예측. 하루 1회면 충분합니다(하루 약 80건).
- 품절·휴무 반영. 주문 DB에 그 정보가 없어서 못 합니다. 나중에 받으면 개선 가능.
