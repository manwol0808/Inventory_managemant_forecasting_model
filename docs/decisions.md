# 결정 사항과 다음 질문

작성일: 2026-09-15, 갱신: 2026-09-16. 결정 상태의 기준 문서다. **확정 방향**은 대화에서 요구한 방향, **제안**은 이번 설계 판단, **미결**은 업무 정의나 데이터 확인이 필요한 항목이다. [첫 기준 모델 탐색 결과](evidence/baseline-v1.md)를 확보했으며 운영 적용 승인은 미정이다.

## 확정 방향

| ID | 방향 | 이유 |
|---|---|---|
| A01 | 현재 실험은 재구매 시점을 우선하고 수량 ±1·±2개 적중률을 함께 관리 | 2026-09-16 후속 요청으로 전환. 최초 수량 RMSE 우선 실험의 결과는 당시 기준 그대로 보존 |
| A02 | 3D 원점 거리와 z-score로 Champion을 선정하지 않음 | 우선순위를 직접 표현할 수 있음 |
| A03 | 같은 상품 구매가 여러 행에 있다고 바로 삭제하지 않음 | 상품·옵션·분할 처리 정보를 보존해야 함 |
| A04 | 원본, 현재 설계, 대화 이력을 분리해서 보관 | 데이터와 결정 경위를 다시 확인할 수 있어야 함 |
| A05 | baseline을 먼저 측정하고 KR 숫자를 확정 | 제시된 20%·10%p는 측정 결과가 아님 |
| A06 | 각 주문 아이템을 끝까지 추적하고 집계 후에도 원본 연결 보존 | 사용자의 후속 확인: 행이 같아 보여도 아이템별 추적이 필요 |
| A07 | 학습 진행과 평가 결과를 Grafana로 상세 추적 | 사용자의 후속 요청. 패널·수집 경로는 [추적 설계](observability.md)에 정의 |
| A08 | 첫 학습 모델은 XGBoost | 사용자가 명시한 모델. 목적함수와 설정은 목표/단위 확인 후 결정 |
| A09 | 주문 이력으로 재구매 상품과 수량을 예측해 앱의 자동 장바구니에 활용 | 2026-09-16 사용자 설명. 구매 이력 기반 예측으로 시작 |
| A10 | 현재 챔피언은 사용자가 지정한 최근 이력 XGBoost | [등록과 벤치마크](champion-benchmarks.md). 다른 평가 조건의 점수를 합친 종합 우승이나 앱 자동 적용 승인은 아님 |

## 이번에 채택한 설계 초안

| ID | 제안 | 판단 및 변경 조건 |
|---|---|---|
| P01 | 단일 로컬 배치 파이프라인 | 파일 규모와 현재 단계에서 작업·결과 재현부터 확보. 서비스는 운영 요구가 생기면 추가 |
| P02 | 원본 → 정제 → 주문/상품 이력 → 시점별 피처·라벨 → baseline → 후보 학습 → 평가 → 선정 | 각 단계의 계약과 실패 원인을 분리 |
| P03 | 집단별 모델 분리보다 전체 고객·상품을 함께 학습하는 모델부터 비교 | 짧은 이력에 대한 초기 가설. 집단 분리는 시간 검증에서 개선될 때만 채택 |
| P04 | 시기 조건 AND 각 주요 집단의 동일 집단 baseline 비교 | 좋은 한 지표가 다른 실패를 상쇄하지 않음 |
| P05 | 학습과 독립 평가 역할 분리 | 평가자는 모델 구조를 좋아하는지보다 고정된 기준으로 성능을 확인 |
| P06 | 규칙 기반 고객군·상품군으로 시작 | 군집 알고리즘 도입 전에 설명 가능한 성능 단면 확보 |
| P07 | XGBoost native categorical 경로를 우선 검토하고 ID의 숫자 크기 해석 방지 | [범주 사전·신규 범주·저장 규칙](data-contract.md). 사용자 지적에 따라 별도 검증 계약 추가 |

|---|---|---|---|---|
| 1 / D01 | 고객·상품별 다음 정상 재구매 날짜와 그날 개수 | 날짜 도래 시 앱 장바구니 반영; 다른 상품 주문은 0 정답 아님 | [v1 계약](purchase-policy-v1.md) 고정. 앱 중복 추가 등 운영 규칙은 8단계 | 일별 이력·정답 생성 |
| 2 / D02 | 현재 모델의 단위 확정: 선택한 옵션의 개수 | prod_no와 수량을 그대로 사용, 중량 환산 없음. 옵션 선택은 앱 담당 | CSV의 옵션 혼합 여부는 미확인이나 초기 진행의 선결 조건에서 제외 | 반복 행 확인 및 개수 기준 이력 준비 |
| 3 / D03 | v1 상태 정책 적용 완료 | 정상 완료만 포함, 취소 제외, 반품·교환·부분 취소·진행 중 보류 | [규칙과 평가 제한](purchase-policy-v1.md); 실제 상태 변경 시각은 미확보 | 4단계 정제 구현 |
| 4 / D04 | CSV 반복 행의 원인은 무엇인가? | 주문 상세 식별자로 추출 중복과 실제 구매를 구별 | 원본 SQL, order_line_id, option_id, 섹션/출고 ID | 반복 개수·금액 일치 여부 확인 |
| 5 / D05 | 평균 수량·대표 수량·재고 서비스 수준 중 무엇을 맞출 것인가? | 첫 탐색 실험은 RMSE 주지표를 결과 계산 전에 고정, MAE 등 보조 보고 | 업무상 과소·과다 비용은 미정; 변경 시 새 평가 버전 | 동일 기준 XGBoost 비교 |
| 6 / D06 | 시기 오차는 며칠까지 허용 가능한가? | 날짜 MAE와 허용 일수 내 비율부터 측정 | 리드타임, 알림/발주 준비에 필요한 시간 | baseline 정의 |
| 7 / D07 | 어떤 집단까지 통과를 보장할 것인가? | 이력량·재구매 간격·상품 인기도 기준, 표본 수와 coverage 동반 | 정제 후 분포, 주요 업무 집단 | 집단 정의안 작성 |
| 8 / D08 | KR 한도와 최소 개선폭은 얼마인가? | 개발용 baseline 결과와 업무 허용치로 고정 | D01–D07, 시간 검증 결과 | Champion 판정 알고리즘 설계 |

D04의 상세 식별자·분할 구조 조사는 완료했고 합산 범위는 v1 계약을 따른다. 전체 이력 확장·최근 가중치 비교와 첫 최종 시간 구간 평가 이후, [주기·확률·TabPFN 비교](evidence/timing-model-comparison-v1.md)까지 완료했다. 새 비교 결과를 운영 모델에 적용하지 않았다. 모델 개선과 함께 앱 저장소·업무 기준 확인 및 실제 미래 로그 검증이 남아 있다. 기존 최종 시험 구간은 사용 완료했다. D02의 개수 기준과 앱의 옵션 처리는 다시 묻지 않는다. 날짜 ±7일은 보고 지표이며 D06의 업무 허용 한도로 확정한 것이 아니다. 답이 없는 업무 한도는 미결로 유지하고, 승인과 실험 전 의사결정을 구분한다. 단순 구현·점검 작업마다 재승인을 요구하지 않는다.

사용자는 주기를 더 중요하게 보고 수량 ±1·±2개 오차를 함께 평가하며 다양한 후보를 비교하도록 요청했다. [주기 비교 v2](timing-experiment-v2.md), [생존분석](survival-experiment-v1.md), TabPFN 순서로 개발 비교를 진행한다. 평가 기회의 구매 확률은 실제 재고 소진 확률과 다르다. 후보 비교 허용은 운영 적용 승인이나 업무상 통과율 확정이 아니다. 이미 확인한 최종 시험을 새 독립 시험으로 재사용하지 않는다.

## 대화 이후 보완한 판단

- 이전 응답의 수량 WAPE는 **후보 지표**다. 재고 기대 수량을 예측하는 경우 WAPE 단독 최적화가 적합한지는 별도로 확인한다. [이유와 대안](evaluation.md), [연구 R02·R03](research.md).
- min–max와 최악 집단 오차만으로는 집단별 악화를 충분히 제어하지 못한다. 집단마다 그 집단 baseline과 비교한다.
- 고객·상품의 행을 합치는 작업과 고객·상품별 학습 모델을 분리하는 작업은 서로 다르다.
- 장기 미구매와 다음 주문 미관측은 구분한다. 관측 종료 때문에 아직 정답을 모르는 경우가 있다.
