# 에이전트와 스킬 운영

## 운영 방식

주 에이전트 한 명이 결정과 통합을 담당한다. 정의가 미결인 초기에는 주 에이전트가 순서대로 처리한다. 독립적인 구현/검토 작업이 생기면 아래 역할을 분리한다. 동시에 여러 역할을 실행해야 한다는 뜻은 아니다.

| 역할 | 입력 | 책임/산출물 | 경계 |
|---|---|---|---|
| 조정·설계 | 현재 결정, 사용자 답변 | 우선순위, 계약, 통합 결과 | 지표를 실험 결과에 맞춰 바꾸지 않음 |
| 데이터 | 데이터 계약, 원본/SQL | 상세 추적, 정제, 피처, 수량 대사 | 임의 중복 삭제·미래 데이터 집계 금지 |
| 모델 | 동결된 예제/평가 계약 | baseline·후보와 예측 테이블 | 테스트 정답으로 튜닝 금지 |
| 평가·검토 | 계약, 예측, 실제값, 출처 | 독립 재계산, 누수 점검, 가드레일 판정 | 모델 작성자의 해석을 점수 근거로 쓰지 않음 |

평가 역할은 정답을 실제 데이터에서 받아야 한다. 별도 에이전트가 동의했다는 사실만으로 모델이 검증된 것은 아니다. 원본 의미는 데이터 담당자 확인과 대사로 검증한다.

## 작업 인계 형식

각 작업은 `목표 / 입력 버전 / 수정 가능한 파일 / 산출물 / 완료 조건 / 미결 사항`을 전달한다. 결과는 `변경점 / 실행한 명령 / 실제 결과 / 남은 문제`로 돌려준다. 여러 작성자가 같은 파일을 동시에 바꾸지 않는다. 전처리 계약이 미결인데 모델 에이전트가 자체 규칙을 정해 진행하지 않는다.

첫 분리 작업은 설계 문서를 대화 맥락 없이 읽는 검토다. 이후 데이터와 모델 구현은 계약이 확정된 다음 진행한다. 모델 실행 비용·실험 횟수도 실제 실행 전에 제한한다.

## 사용할 스킬

이 목록은 이번 환경에서 제공된 스킬의 이름과 적용 시점이다. 매번 전부 실행하지 않는다. 스킬은 연구/구현을 돕는 절차이며 실제 평가 코드를 대체하지 않는다.

| 스킬 | 적용 시점 | 이번 작업에서의 사용 |
|---|---|---|
| readchk | 요구가 길거나 목표가 여러 갈래일 때 | 요청 해석과 미결 목표 구분 |
| spreadsheets:Spreadsheets | CSV 구조·집계 또는 스프레드시트 결과를 다룰 때 | 원본 읽기와 수량/중복 의미 확인 원칙 |
| mandela | baseline·검증·Champion 규칙 설계/변경 | 미래 정보, 순환 평가, 사후 집단 정의 점검 |
| factchk | 논문·기법·외부 사실을 근거로 쓸 때 | 원문/저자 자료 확인, 적용 주장과 사실 분리 |
| sip | 문서/코드를 작성한 후 전달 전 | 관련 검토를 묶어서 실행 |
| shower | 독립적인 문서 인계 점검이 필요할 때 | 대화 맥락 없는 검토 에이전트가 모호한 계약 확인 |
| ssotize | 값·정의가 여러 문서에서 어긋나는지 확인할 때 | 이번에는 읽기 전용 일관성 감사 |
| re0 | 문서가 반복 수정으로 길어졌을 때 | 중복 설명과 과거/현재 혼동 정리 |

`hate`, `macrothink`, `re0-loop` 같은 사용자 호출 중심의 확장 절차를 자동으로 추가하지 않는다. 프로젝트 전용 학습 스킬은 baseline까지 실제로 한 번 실행해 재사용할 절차가 확인된 뒤 필요성을 판단한다. 지금은 검증되지 않은 학습 절차를 스킬로 고정하지 않는다.

## 매 작업 종료 시

1. 문서 상태와 실제 구현/실행 상태가 일치하는지 확인한다.
2. 결과의 원본/데이터 해시·설정·평가 버전을 연결한다.
3. 데이터 또는 지표가 바뀌면 영향을 받는 산출물을 식별한다.
4. 결정 문서와 해당 날짜의 대화 기록을 갱신한다.
5. 다음 행동 하나와 이를 막는 정보가 있으면 명시한다.

일상 점검은 로컬 데이터·파일을 사용한다. 도구 설치·외부 전송·실제 배포는 해당 실행 환경의 권한과 사용자 지시를 따른다. 이 문서는 권한을 우회하는 실행 지침이 아니다.
