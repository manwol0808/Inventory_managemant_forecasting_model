# 데이터와 피처 계약

설계 v0. 원본 집계의 기준은 [data-profile.json](evidence/data-profile.json)이며, [점검 스크립트](../scripts/audit_csv.py)로 재현한다. 전체 상태를 포함한 구조 점검으로, 정제된 수요 통계는 아니다.

## 원본에서 확인한 사항

- 전체 UTF-8 디코딩 성공, 대체 문자 `�` 0개, 모든 데이터 행 14열. 이 결과는 필드 의미까지 올바르다는 뜻은 아니다.
- 40,910행, 주문 14,987개, 고객 3,959개, 상품 코드 777개. 관측 주문일 범위는 2026-04-09부터 2026-09-15까지 160일이다.
- 주문별 여러 행: 8,204건. 고객×주문×상품 반복 키: 1,857개, 해당 키의 첫 행을 제외한 나머지 행: 7,460개.
- **14열 전체가 같은 반복 그룹 1,706개, 첫 행 이후 반복 행 7,186개.** SQL 조인 중복인지, CSV에서 빠진 옵션 차이인지는 미확인이다. 완전 일치만으로 삭제하지 않는다.
- 고객×상품 조합 19,312개 중 14,155개는 주문번호 기준 이력이 1회다. 고객 중 1,620명도 관측 기간 내 주문이 1회다. 가입 이후 전체 이력이 1회라는 뜻은 아니다.
- 같은 고객이 같은 날 주문번호 여러 개를 가진 경우 677 고객·일이다. 날짜 단위 간격 계산에 주의한다.
- 주문번호 안에서 고객 코드·주문일·주문총액·결제금액의 값 충돌은 없었다. 금액은 주문당 한 번만 집계할 수 있는 구조로 관측되지만, 금액의 업무 의미는 별도 확인한다.
- 수량은 현재 양의 정수이며 최댓값은 499다. 큰 수량을 자동으로 이상치 삭제하지 않는다. 원본 합계는 중복/옵션 해결 전이므로 실제 수요로 쓰지 않는다.
- 등급 10,985행, 가입일 203행이 비어 있다. 고객명·연락처 누락 여부는 모델 대상 선정 조건으로 사용하지 않는다.

## 사용할 행과 집계 규칙

1. 원본은 보존하고 파생 데이터에 원본 파일 해시와 CSV 레코드 순번을 부여한다. 레코드 순번은 추적 키이지 주문 상세의 업무 식별자가 아니다.
2. 키 누락·날짜/수량 파싱 실패·단위 불명·키 충돌은 사유를 달아 격리한다. 보고에서 제외 규모를 숨기지 않는다.
3. `order_line_id`와 옵션·섹션 정보를 확보해 중복 원인을 확인한다. 조인 증식은 SQL/추출 단계에서 고치고, 서로 다른 실제 상세는 유지한다.
4. 같은 고객·주문·SKU의 실제 상세는 정답의 상태 규칙에 따라 수량 합산한다. 옵션이 다른 상품을 하나의 SKU로 합치지 않는다.
5. 상품 행이 여러 개인 주문에서 주문 금액을 반복 합산하지 않는다. 주문 금액을 상품별 매출로 배분할 때는 상세 금액이 필요하다.
6. 여러 주문번호가 같은 날에 있으면 **주문 테이블에는 별개 주문으로 보존**한다. 일 단위 시기 목표에는 고객×주문일 이벤트 테이블을 따로 만들어 0일 간격 문제를 피한다. 주문별 시각이 필요하면 timestamp를 요청한다.
7. 신규·희소 고객/상품은 제거하지 않고 fallback 대상으로 구분한다. 평가 대상 정의는 결과를 보기 전에 고정한다.

### 상태 처리 초안

| 상태 | 정제 시 처리 초안 |
|---|---|
| PURCHASE_CONFIRMATION, SHIPPING_COMPLETE | 이행된 구매 후보. 순수요 정의라면 반품 연결도 확인 |
| SHIPPING, SHIPPING_READY | 진행 중 구매로 보존. 최신 기간의 미확정 라벨로 표시 |
| CANCEL_COMPLETE | 취소 라인에 연결. 최초 주문/출고/순수요 중 선택한 목표에 맞게 처리 |
| RETURN_COMPLETE | 원주문·반품 수량·재입고 여부 확인. 전체 주문을 통째로 삭제하지 않음 |
| EXCHANGE_PURCHASE_CONFIRMATION | 교환 전후 상세 연결 후 추가 수요/대체 출고 구분 |
| 새 상태 | 규칙 미등록으로 처리하고 뜻 확인 |

현재 파일만으로 부분 취소/반품 수량을 알 수 없다. 상태명을 보고 반품 수량을 음수로 추정하지 않는다. 최종 상태로 라벨을 정의하더라도 피처의 과거 관측 가능성을 별도로 보장한다.

## 학습 데이터의 한 행

### 주문 아이템의 추적 계층

사용자의 후속 요구에 따라 아이템별 추적을 유지한다. **학습용 집계는 별도의 뷰이며 원본 상세를 대체하지 않는다.**

| 계층 | 키 | 보존 내용 |
|---|---|---|
| 원본 레코드 | 파일 해시 + CSV 레코드 순번 | 원본의 모든 행, 수량, 상태 |
| 주문 상세 아이템 | 원본 DB의 order_line_id + 필요한 옵션/섹션 키 | 주문 안의 SKU·옵션·수량·상태 이력 |
| 학습용 상품 이벤트 | 고객 + 주문/구매일 + SKU | 목표 정의에 맞춰 합산한 수량 |
| 연결 테이블 | 원본 레코드 키 ↔ 상세 아이템 키 ↔ 상품 이벤트 키 | 포함/제외/병합 사유와 수량 기여분 |

현재 상세 ID가 없으므로 원본 행에는 임시 추적 키만 부여할 수 있다. 이 키를 실제 고유 구매의 증거로 간주하지 않는다. 상세 ID 확보 후 추출 중복으로 판명된 행도 원본에는 남기고, 정제 계층에서 하나의 상세에 연결해 중복 수량만 집계에서 제외한다. 서로 다른 실제 구매 상세는 모두 유지한다. 한 상세의 수량이 5라는 이유만으로 물리적 개별 상품 5개의 일련번호를 알 수 있는 것은 아니다.

검증 계약: 모든 집계 수량은 연결 테이블의 기여 수량 합과 일치해야 한다. 모든 원본 행은 포함 또는 사유 있는 제외로 추적 가능해야 한다. 특정 고객·주문·상품의 예측 오차를 해당 원본 상세까지 역추적할 수 있어야 한다.

### 예측 목표별 예제

최종 선택은 [D01](decisions.md) 이후 확정한다.

- **기간 수량:** `customer_id × sku_id × origin × H`. 정답은 `(origin, origin + H]`의 수량 합이다. 입력은 origin 시점까지 알려진 이력이다.
- **다음 주문 수량:** origin 이후 첫 고객 주문 이벤트의 SKU별 수량. 다음 고객 주문에서 빠진 SKU의 수량은 0이다. 해당 SKU를 다시 사는 시점까지 기다리는 목표와 혼동하지 않는다.
- **다음 주문 시기:** 고객의 다음 구매일까지 남은 일수. 고객×SKU의 다음 구매일은 별도 목표로 관리한다.

기간 수량 모델의 대상 SKU 집합은 예측 시점의 카탈로그와 과거 이력으로 만든다. 처음에는 관측된 고객×SKU 재구매 조합을 핵심 범위로 삼는 안을 검토하되, 신규 고객·첫 SKU 구매는 별도 fallback/집계 예측으로 추적한다. 미래에 실제로 산 조합을 역으로 골라 학습/평가 대상을 만들지 않는다. 전체 고객×전체 SKU를 무조건 곱해 노출되지 않은 조합을 모두 0으로 만드는 것도 피한다. 범위 밖 실제 수량, 포함 비율, fallback 성능을 함께 보고한다.

원본에 행이 없다고 항상 무수요는 아니다. 판매 가능 기간·고객의 관측 시작·추출 범위를 확인한 구간에만 0을 채운다. 품절 정보가 없으면 관측 주문량을 잠재 수요로 해석하지 않는다.

## 초기 피처 목록

| 단위 | 피처 | 시점 규칙 |
|---|---|---|
| 고객 | 마지막 구매 후 경과일, 과거 구매일 수, 최근 구매 간격·중앙값·변동성 | 고객×구매일 이벤트에서 origin 이전 이력만 |
| 고객×SKU | 직전 수량, 최근 수량 평균/중앙값, 구매 후 경과일, 양수 구매 횟수 | 확정된 단위와 정제 라인 사용 |
| 고객×SKU | 최근 7/28/56일 수량·구매일 수·미구매 비율 | 기간은 실험 후보. 관측 전 구간을 0으로 채우지 않음 |
| SKU | 과거 판매 수량, 구매 고객 수, 최근 추세, 인기 구간 | 전체 데이터로 미리 집계하지 않음 |
| 고객 | 과거 주문당 지출, 사업자 여부, 가입 경과일 | 과거에 알 수 있었던 필드만, 주문 금액 중복 제거 |
| 달력 | 예측 기준일의 요일/월, 앞으로 예측할 날짜 | 미리 알려진 달력만. 캠페인·가격은 당시 알려진 계획이 있어야 함 |
| 이력 품질 | 이력 길이, 관측 가능 일수, 결측/신규 표시 | 이력이 짧은 것과 수요가 없는 것을 구분 |

고객군은 이력 부족/충분, 간격, 규칙성으로 시작하고 상품군은 과거 판매량·구매 빈도로 시작한다. 실제 경계값은 개발 학습 구간으로 정하고 같은 fold의 후보 모두에 동일하게 적용한다. 최종 테스트 결과에 따라 집단을 다시 나누지 않는다.

## XGBoost의 categorical features

상품·고객 코드처럼 **구분을 나타내는 값**과 수량·경과일처럼 **크기를 나타내는 값**을 구별한다. 상품 코드 100과 200 사이에 수량처럼 두 배라는 의미는 없다. 코드를 정수로 바꿔 연속형 피처로 넣으면 `< 150` 같은 임의 순서의 분기를 허용하게 된다.

| 필드 | 모델 입력 제안 | 주의 |
|---|---|---|
| SKU/product_id | native categorical 후보 | 아이템 추적 키는 계속 유지. 피처로 사용/제외한 모델을 개발 backtest에서 비교 |
| customer_id | 초기 모델 피처에서 제외 | 고객 이력 집계로 표현. 키는 유지하고, ID 사용은 후속 별도 실험 |
| order_id | 피처 제외 | 주문 식별·대사에만 사용 |
| 고객 등급 | 시점 검증 후 categorical | 등급 코드에 임의 순서를 주지 않음 |
| 사업자 여부 | boolean 또는 0/1 | 실제 이진 값 의미로 사용 |
| 고객군·상품군 | 과거 정보로 만든 categorical | 테스트 오차를 보고 그룹을 만들지 않음 |
| 상품명 | 초기 텍스트 피처 제외 | SKU/규격 확인에 사용 |
| 최근 수량·경과일 | numeric | 범주형으로 변환하지 않음 |

Python DataFrame의 해당 컬럼을 `category` dtype으로 준비하고 `enable_categorical=True`, `tree_method="hist"`를 쓰는 경로를 초기 제안으로 둔다. 지원 경로에서 모델은 `.json` 또는 `.ubj`로 저장한다. 학습/예측 dtype과 범주 매핑 일치가 필요하며, XGBoost 3.1 이상 Python 인터페이스의 auto-recoding도 신규 범주의 의미를 학습해 주지는 않는다. [공식 categorical 안내](https://xgboost.readthedocs.io/en/stable/tutorials/categorical.html).

프로젝트 처리 규칙은 다음과 같다.

1. 범주 사전·dtype·컬럼 순서는 `train_core`에서 정하고 전처리와 함께 저장한다. 최종 재학습 시에도 해당 학습 범위만으로 새 버전을 만든다.
2. train/test마다 따로 정수 코드를 붙이지 않는다. `cat.codes`만 꺼내 연속형 숫자로 전달하지 않는다.
3. 검증/운영의 신규 범주는 기존 범주 번호로 억지 매핑하지 않는다. 미등록 표시를 먼저 보존하고, 학습 사전 밖 값은 missing 처리와 신규 피처 표시 또는 사전에 정의한 fallback으로 연결한다. 어떤 경로를 택했는지 기록하고 unseen 집단 성능을 별도 평가한다.
4. 학습 데이터에 전혀 없던 `OTHER`라는 이름을 만들어 두는 것만으로 신규 상품 예측을 학습했다고 보지 않는다. 실제 드문 범주의 통합은 업무 의미와 학습 표본이 있을 때만 검토한다.
5. 고유값이 많은 ID를 native categorical로 지정해도 과적합이 자동 해결되지는 않는다. ID 포함/제외 비교, 신규 SKU 성능, 정규화·복잡도 제한으로 판단한다.
6. target encoding은 초기에는 사용하지 않는다. 나중에 도입하면 각 행의 미래/자기 정답이 인코딩에 들어가지 않도록 시간 순서에 따른 학습 내부 계산이 필요하다.

이 규칙은 설계이며 아직 dtype 변환이나 XGBoost 학습을 실행하지 않았다. 설치 버전을 고정한 뒤 범주 순서 변경·일부 범주 누락·새 범주·결측·모델 저장/재로딩에 대한 예측 일치/예외 테스트를 수행한다.

## 데이터 담당자에게 받을 항목

우선순위: ① 원본 추출 SQL과 추출 시각/범위 ② 주문 상세·옵션 ID ③ SKU/옵션별 규격과 수량 단위 ④ 부분 취소·반품 이력과 수량/시간 ⑤ 주문 timestamp와 과거 등급/가격 ⑥ 판매 가능·품절 이력. 재고 발주까지 확장할 때 현재고·입고예정·리드타임·최소 발주량을 추가한다.

SQL 확인 시 주문 헤더→상세는 일대다, 상세→옵션/섹션/결제 조인은 더 많은 행으로 늘 수 있음을 확인한다. 각 조인 전후 상세 ID별 건수·수량을 대사한다. 원본 DB나 SQL에 실제로 접근한 상태는 아니다.
