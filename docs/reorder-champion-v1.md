## 이 숫자가 어떻게 나온 것인지 — 실제 장바구니가 아니다

**앱 연동은 없고, 장바구니에 담은 적도 없다.** 전부 과거 주문 이력을 재생한 사후 대조다.

주문 이력에는 각 구매 건의 다음 구매일(`target_on`)이 이미 들어 있다. 여기에 우리 규칙이 정했을 **가상의 담는 날**을 계산해 두 날짜를 비교한다.

```
2026-01-02  A카페 원두 구매          ← origin_on   (과거 기록)
2026-01-12  규칙이면 여기 담았을 것    ← cart_on     (계산한 가상 날짜)
2026-01-30  A카페 원두 재구매         ← target_on   (과거 기록)
                                      제때 담김, 대기 18일
```

**늦음**은 계산한 담는 날이 실제 구매일보다 뒤인 경우다. 실시간 관측이 아니다.

따라서 모든 수치는 **사장님의 구매 행동이 장바구니 제안에 전혀 영향받지 않는다**는 가정 위에 있다. 실제로는 담긴 것을 보고 주문을 앞당기거나 미룰 수 있고, 그러면 `target_on` 자체가 달라진다. 운영 성능은 연동 후 새 로그로만 확인된다. 현재 배치는 `mode: preview_only`, `auto_apply: false`다.

운영에서 늦음은 오히려 재기 쉽다 — 담을 예정일 전에 그 품목 주문이 들어오면 늦음이다. 주문 이벤트만으로 잡힌다. 설계가 필요한 쪽은 반대다. 담겨 있는데 사지 않고 지우는 경우는 삭제 로그가 없으면 보이지 않는다. 규칙 3의 짝별 보정은 늦음 신호만으로 도는 구조라 연동 직후부터 작동할 수 있다.

## 구성

**담는 날 규칙은 기존 그대로 둔다** — 예측 재구매일 7일 전 이전 월요일, 직전 구매일 이후로 하한. 바뀐 것은 셋이다.

1. **수량** — 매장×날짜×품목 장바구니 모델의 수량 예측으로 교체한다.
2. **담는 날 앞당김** — 매장 주문 리듬 모델의 예측일이 더 이르면 그쪽으로 당긴다. 앞당김은 최대 7일.
3. **짝별 온라인 보정** — 그 고객×품목의 과거 예측 오차 중앙값만큼 담는 날을 당긴다. **앞당김만 허용하고**(늦음은 0점이므로 한쪽으로만 움직인다) 한도는 7일이다. 직전 구매까지의 결과만 쓰므로 인과성을 지킨다. 검증 건의 29.1%에 보정이 걸린다.

## 판단 기준 — 순진한 규칙을 이기는가

예측 없이 **구매 다음 월요일에 무조건 담는 방식**을 기준선으로 둔다. 코드 한 줄이면 되는 이 방식보다 나아야 예측 모델이 값을 한다.

담긴 뒤 실제 구매까지의 **대기**가 짧을수록 제때 담은 것이고, **늦음**(담기 전에 이미 삼)은 그 주기를 0점으로 만든다. 담는 날을 앞당기면 늦음은 줄지만 대기가 늘고, 끝까지 밀면 순진한 규칙이 된다.

**모델이 순진한 규칙 대비 버는 것은 약 6.6%p다.** 14일 안 적중 41.4% → 47.6%, 21일 안 적중 55.3% → 61.9%. 특히 꼬리에서 크다 — 순진한 규칙은 열 건 중 한 건이 55일간 장바구니에 박혀 있는데 챔피언은 44일로 줄인다. 대가는 늦음 3.7% → 8.4%다.

## 채택하지 않은 것 — 담는 날을 앞당기는 규칙

담는 날 규칙 25가지를 시험했다. 균일 앞당김, 비례 앞당김, 주기 하한, 월요일 스냅 변형, 예측 보정표, 구간별 오프셋, 구매 후 고정일 담기, 계층 규칙, 예측 버킷별 완전탐색.

**전부 21일 안 적중을 못 올렸다.** 예측 간격만 입력으로 쓰는 규칙의 상한을 완전탐색으로 구했을 때 현행 대비 +0.2%p였다. 담는 날 규칙은 늦음과 과도 조기 사이에서 자리만 바꾼다.

특히 **구매 후 고정일 상한(예: 무조건 14일 안에 담기)은 채택하지 않았다.** 늦음을 줄이고 긴 주기 담겨있음을 95%로 올리지만, 예측 46일짜리를 구매 후 10일에 담아 40일 넘게 기다리게 한다. 그건 예측이 아니라 순진한 규칙이며 21일 안 적중이 내려간다.

## 표본이 쌓이면 나아지는가 — 아니다

검증셋을 고정하고 학습 기간만 늘렸다.

| 학습 기간 | 학습 건수 | MAE | 21일 안 적중 |
|---|---:|---:|---:|
| 2025-12 | 1,936 | 12.29 | 59.6% |
| 2025-10~12 | 4,537 | 12.20 | 59.6% |
| 2025-08~12 | 8,434 | 12.36 | 59.5% |
| 2025-07~12 | 10,082 | 12.68 | 59.4% |

**1개월 1,936건이 6개월 10,082건과 같다.** 학습곡선이 이미 평평하고, 오래된 데이터를 넣으면 오히려 조금 나빠진다.

같은 피처로는 표본 수가 병목이 아니다. 피처 중요도 상위가 전부 과거 간격 통계(`gap_median_days`, `pair_median`, `pair_gap_lag1~3`)이고, 재고 수준·소비 속도 같은 직접 신호가 주문 자료에 없다. 예측 간격 22-30일 구간의 실제 간격 표준편차가 20.5일이며, 같은 이력을 가진 매장이 이번엔 17일 뒤에 사고 다음엔 42일 뒤에 산다.

**필요한 것은 표본이 아니라 새로운 종류의 데이터다.** 장바구니 삭제 로그, 앱 열람 로그, 실측 소진일.

## 기본 모델은 바꾸지 않는다 (2026-09-18 추가 측정)

간격 예측 모델 자체를 바꾸는 방향을 다섯 가지로 시험했고 **전부 기각했다.** 판정은 월별 워크포워드 12폴드에서, 담는 날 규칙을 모두 적용한 같은 채점기로 했다.

| 시험한 변경 | 결과 | 판정 |
|---|---|---|
| 기존 21피처 모델의 분위를 0.7로 | 늦음 9.5% → **19.3%**, 21일 안 적중 59.7% → 57.3% | 기각 |
| enriched 64피처로 기본 모델 교체 | 12폴드 전체 61.9% → **61.6%** | 기각 |
| 학습 창 365 / 730 / 1100일 | 세 값이 동일 | 기각 |
| 학습을 예측 대상 모집단으로 제한 | 58.6% → 56.8% | 기각 |
| 매장 주문 리듬을 피처로 투입 | ±0.3%p, 기간마다 부호가 바뀜 | 기각 |

**분위 변경은 단일 검증셋이 정반대를 가리켰다.** 소진된 검증 코호트 1,196건에서 분위 0.7은 날짜 MAE 5.559 → 5.154, 편향 −3.887 → −1.667, ±7일 적중 73.0% → 75.1%로 모두 개선으로 보였다. 그 지표가 **±7일 대칭**이기 때문이다. 우리 목적은 대칭이 아니다 — 늦으면 0점이고 일찍은 회복 가능하다. 분위를 올리면 예측이 길어져 담기가 뒤로 밀리고 늦음이 두 배가 된다. 워크포워드로 확인하지 않았으면 그대로 넣을 뻔했다.

**enriched 피처 교체는 기간마다 부호가 뒤집힌다.** 선택 구간(2025-10~12)에서는 현행이 61.4%로 이기고 확인 구간(2026-01~06)에서는 enriched가 60.2%로 이긴다. 12폴드 전체로는 7승 5패에 −0.3%p이며, 진 폴드의 낙폭이 크다(2025-08 −5.0%p, 2025-10 −5.4%p).

이전 기록에서 재학습 모델이 62.1%로 나왔던 것은 **2025-07~12로 한 번 학습해 2026-01~06을 예측한 단일 분할**이었다. 운영처럼 폴드마다 재학습하면 61.6%다. 단일 분할 추정이 낙관적이었으므로 그 수치는 폐기한다.

기각한 변경들의 코드는 남기지 않았다. 재현이 필요하면 이 표의 조건을 다시 구성하면 된다.

## 운영 코드 반영 (2026-09-18)

규칙 1·2·3이 배치에 들어갔다. 셋 다 선택 입력이며 하나도 주지 않으면 **기존 동작과 완전히 동일**하다(16,140행 전수 대조에서 차이 0개).

```bash
.venv/bin/python -m scripts.pair_adjustments record <관측된 예측CSV>

.venv/bin/python -m scripts.router_champion predict \
  --as-of 2026-09-16T00:00:00+09:00 --output artifacts/<새 폴더> \
  --store-rhythm <매장 리듬 예측CSV> \
  --adjustments-db data/pair-adjustments-v1.sqlite
```

- **`scripts/pair_adjustments.py`** — 짝별 보정 저장소. 고객×품목마다 과거 예측 오차를 쌓고 중앙값만큼 담는 날을 당긴다. 앞당김만 적용하고 한도는 7일이다. `origin_event_id` 기준 멱등이므로 재실행해도 이력이 중복되지 않는다. 배치는 무상태이므로 이 저장소가 실행 사이의 기억을 맡는다.
- **`scripts/router_champion.py`** — `--store-rhythm`으로 수량을 교체하고 담는 날을 최대 7일 당긴다. `--adjustments-db`로 짝별 보정을 적용한다. 출력에 `pair_adjustment_days`, `scheduled_gap_days`, `store_rhythm_on`, `store_rhythm_pulled`, `router_quantity` 다섯 열이 추가된다.

2026-09-16 일정으로 실제 실행한 결과, 열린 제안 2,840건 중 담는 날이 1,568건 바뀌고(중앙 4일 앞당김, 뒤로 밀린 건 0건) 수량이 690건 교체된다. 매장 리듬 예측 11,505짝이 적재되어 2,670건을 당기고 4,262건의 수량을 제공하며, 짝별 보정은 3,650짝에서 1,296건에 걸린다.

## 확인하지 않은 것

- **수량은 기존 담는 날 기준으로 계산한 값을 재사용했다.** 규칙 2가 날짜를 당긴 건에 대해서는 그 시점 피처로 다시 뽑아야 최종값이다. 58.4%는 근사치다.
- 매장 주문 리듬 모델의 장바구니 임계값 0.2는 2026-07~08 실험에서 정해져 약한 누수가 남아 있다.
- 장바구니 삭제 로그가 없어 「오래 담겨 있는 비용」을 측정하지 못했다. 늦음과 과도 조기 사이의 교환 비율을 정할 근거가 아직 없다.
- **담기 전 주 단위 재예측은 세 가지로 구현해 전부 실패했다.** 임계 기반 주간 스캔은 21일 안 적중이 59.1%까지 내려갔고, 사건별 가중치로 확장 편향을 보정해도 58.4%였다. 결정적인 것은 「챔피언이 담는 날에 남은 일수를 다시 물어 21일을 넘으면 1주 미룬다」는 최소 버전이 **한 건도 바꾸지 못했다**는 점이다. 피처 62개가 전부 구매 시점 고정값이라 구매와 구매 사이에 새로 도착하는 정보가 없다. 재예측이 값을 가지려면 GA 방문·앱 열람 같은 중간 신호가 필요하다.
- 규칙 3의 보정은 같은 짝이 반복될 때만 걸린다. 39.9%가 대상이고 나머지는 보정 없이 간다. 이력이 무한히 쌓여도 효과는 늦음 −0.7%p 근처에서 멈춘다 — 양방향으로 튀는 짝은 오차 중앙값이 0이라 보정할 것이 없기 때문이다.
- 운영 성능은 새로운 미래 로그로 확인해야 한다.
