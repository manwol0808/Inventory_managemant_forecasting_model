# 2026-09-16 대화 요약

이 파일은 원문 전체가 아닌 사용자 설명과 이번 작업 결과의 요약이다.

- 앱은 카페 사장님의 재고 보충 시점에 상품을 자동 장바구니에 넣으며, ML은 특히 주문 수량을 잘 맞추는 역할이다.
- 약 6개월의 고객 주문 CSV를 정제해 다음 구매를 예측하는 것이 출발점이다. 실제 파일 관측 범위는 160일이다.
- 데이터 충분성 질문에 실제 CSV 반복 구매 분포를 확인했다. 첫 모델 검증은 진행하되 전체 고객 적용 가능성은 이후 기간 성능으로 판단하고 추가 과거 이력 확보를 제안했다. 추가 이력은 아직 받지 않았다.
- 고객별 주문 추적과 과거 수량·간격을 학습 정보로 만든다는 설명 후, 사용자가 작업을 하나씩 설정하고 시작하자고 요청했다.
- [작업 목록](../tasks.md)을 만들고 첫 추적 기반을 구현했다. 원본 모든 행·상태·반복을 보존하는 로컬 SQLite이며 학습용 정제 데이터는 아니다.
- 상품 코드에 여러 옵션이 섞이는지 질문했다. 답 전에는 수량 합산과 단위 추정을 하지 않는다.

- 후속 결정: 앱이 선택 규격을 알고 있으므로 모델은 상품 코드별 개수를 예측한다. 수량 2는 선택한 규격 2개로 처리하고 중량 환산은 하지 않는다. 옵션 확보를 초기 진행 조건에서 제외했다.
- 다음 단계 시작 요청에 반복 조합을 분류했다. 1,857개 중 전 열 동일 1,594개, 일부 값 상이 263개. 행 삭제나 수량 합산은 하지 않았다. 다음 확인은 추출 SQL 또는 주문 상세 ID다.

- 사용자가 BigQuery 직접 조회와 상세 식별자 포함 재추출 진행을 승인했다. 새 읽기 전용 SQL을 작성·실행해 42,511행을 반환했다. 현재 2단계이며, 취소·반품 처리와 학습용 수량 합산은 아직 하지 않는다.

- 사용자가 CSV 저장을 알렸다. 루트의 dataset3·5·6을 합쳐 42,511행 전체를 확보·대조했다. dataset2는 잘린 파일, dataset4는 dataset3과 같은 파일이므로 병합에서 제외하고 원본은 보존했다. 2단계의 추적 데이터 확보·검증은 완료했고 상태별 수량 반영은 3단계로 남긴다.

- 사용자가 학습/검증/테스트 분할 방법, 현재 기간, 최대 확보 기간과 학습 규모 조사를 요청했다. 현재 파일은 160일, 전체 원본에는 2024-10-02~2026-09-16의 약 23.5개월 이력이 있고 최신 주문 55,023건/상품 상세 138,531행을 확인했다. 긴 원본은 아직 내려받지 않았다. 시간순 rolling 검증+잠금 테스트 및 달력 기준 날짜 초안을 평가 문서에 기록했다. 정확한 날짜는 정답/확정 지연을 정한 후 동결한다.

- 사용자가 현재 기간으로 첫 모델을 만들고 점차 과거 이력을 늘리는 방식을 제안했다. 취소 완료 항목의 학습 정답 제외를 승인했고 XGBoost/LightGBM 선택 이유를 질문했다. 취소 완료 1,523행을 제외 대상으로 표시한 상태 검토 파일을 생성·대조했다. 다른 상태와 정답 이벤트는 미결이고 학습은 미실행이다.

- 계속 진행 요청의 해석: 주문·취소·반품·교환의 상세 연결을 조사하고 근거가 확인된 처리 규칙을 준비한다. 확인되지 않은 상태를 임의 합산해 학습하지 않는다.

- 상태 연결 조사 진행 중 사용자는 원두와 시럽을 각각 추적하는 것 아니냐고 확인했다. 상품별 이력을 유지하며 v1 작업 정의를 같은 고객·상품의 다음 재구매 수량으로 잡는다고 설명했다. 다른 상품만 산 주문을 해당 상품 수량 0 정답으로 넣지 않는다.

## 3단계 마무리 요청

사용자가 상품별 시점 도래 시 예측 개수를 장바구니에 담는 목표를 명시하고 남은 3단계 진행을 요청했다. 첫 버전은 정상 구매만 포함하고 애매한 주문·상품은 보류하는 구현 기준을 적용했다. 정책과 시점 평가 제한은 [v1 계약](../purchase-policy-v1.md), 실행 수치는 [집계](../evidence/purchase-policy-v1.json)에 기록했다. 일별 합산 및 보류 장벽은 설계 선택이며 실제 소비량 확정이 아니다. 4단계 이벤트·라벨 생성과 학습은 아직 실행하지 않았다.

## 4단계 진행

사용자가 노션 작업을 건너뛰고 4단계 진행을 요청했다. 정책 판정 파일에서 날짜별 구매 이력·원본 연결·다음 재구매 정답과 미관측 목록을 생성했다. [실행 보고](../evidence/purchase-events-review.md). 노션 수정과 모델 학습은 하지 않았다.

## 내부 테스트와 추천 대상 범위 보완

사용자가 내부 직원의 테스트 구매 제외와 추가 전처리 점검을 요청했다. 내부 회원코드/주문번호와 제외 범위를 질문했다. 현재 자료에서 샘플명 8,596행, 명시적 사은품명 316행, 임시개인결제창/만월플러스명 579행이 기존 정상 이력에 포함됨을 확인했다. 이는 이름 기반 검토 후보이며 제외 확정이 아니다. 4단계를 업무 제외 기준 보완 중으로 갱신했고 기존 파일은 보존했다.

## 첫 학습 전 전처리 범위 계획

사용자가 추가 제외 항목을 검토한 뒤 모델 학습으로 진행할 수 있는지 물었다. [전처리 계획](../preprocessing-plan.md)과 [제외 영향 계산](../evidence/preprocessing-impact-preview.json)을 작성했다. 샘플/명시적 사은품/결제용으로 보이는 23개 상품 코드를 제외하는 가정에서는 13,587쌍 중 667쌍이 빠지고 12,920쌍이 남는다. 실제 제외와 내부 테스트 제외는 미적용이다. 내부 식별정보는 대기 중이며 만월플러스/개인결제창의 실제 용도를 추가 질문했다.

## 만월플러스와 테스트 계정 확인

사용자는 만월플러스가 선불 적립금 충전 상품이라고 설명했고, 테스트 계정명은 테스트라고 알려줬다. 충전 6개 코드를 제외했고 BigQuery 현재 고객 4,044명을 회원 정보와 연결해 이름이 정확히 테스트인 계정 1개를 찾았다. 해당 11행은 모두 취소 완료였다. [v3 결과](../evidence/preprocessing-applied-v3.md). 현금 0원만으로 정상 구매를 제외하지 않는다.

## 샘플·명시적 사은품 처리 완료

사용자가 계속 진행을 요청했다. 샘플 15개와 명시적 사은품 2개 코드를 제외한 v4 구매일·정답을 생성했다. 정상 구매일 29,473개, 정답 12,920쌍이며 정상 동반 상품·고객 이력은 유지했다. 원본 대사·비제외 이력 동일성·재현 해시와 테스트 20개를 확인했다. [실행 결과](../evidence/preprocessing-applied-v4.md). 다음은 5단계이며 학습은 아직 실행하지 않았다.

## 시간 분할과 고객·상품별 이력 구분

사용자가 6:2:2 진행을 요청한 뒤 고객·상품별 재구매 기준으로 나눠야 하는지 질문했다. 고객×상품은 예제/이력의 단위이고 공통 시간 경계는 평가 분할 기준임을 설명했다. 누적 과거 이력 피처와 96/32/32일 탐색용 분할을 생성했다. [계약](../feature-split-contract.md). 최신 상태의 과거 가용성은 검증되지 않아 strict_training_ready=false, 통과 0개로 기록했다. 학습 자체는 미실행이다.

## 기준 모델 실행과 사용자 질문

사용자가 시작을 요청해 직전 수량·간격 중앙값 기준 모델을 적합하고 검증 1,196쌍을 평가했다. [실행 결과](../evidence/baseline-v1.md). Grafana 최소 구성을 로컬에서 실행했고 테스트 33개와 파일·화면 대사를 확인했다. XGBoost와 최종 시험은 미실행이다.

사용자는 6→1→4→2개처럼 변동하는 주문에서 학습하는 방법, 유행 급증을 별도 모델로 결합할 필요, 1개 또는 한 번만 구매한 경우의 현재 예측, Grafana 각 패널과 6회 이상 집단의 MAE 3.99 해석을 질문했다. 과거 입력→실제 다음 주문의 학습 예제, 현재 모든 수량은 직전 반복이라는 점, 고객·상품별 시점의 이력 횟수와 날짜/수량 MAE 차이를 설명했다. 스파이크 모델은 아직 구현하지 않았고 과거 시점까지 알려진 상품 추세 피처부터 비교하는 후속 방향을 기록했다.

## XGBoost 첫 학습 완료와 그래프 수정

사용자가 계획대로 실행을 요청해 수량·재구매 간격 XGBoost 모델을 학습하고 같은 검증 1,196쌍으로 비교했다. 최종 학습은 6,579쌍, 피처 21개, 선택 반복 수는 수량 90회·간격 124회다. [실행 결과](../evidence/xgboost-v1.md). 수량 RMSE와 날짜 MAE는 개선했지만 연속 수량 MAE와 정수 정확 일치율은 악화했다. 최종 시험은 사용하지 않았고 전체 이력 학습은 다음 단계다.

사용자는 MAE·RMSE 의미, Grafana 학습곡선 오류, 학습이 아직 진행 중인지 질문했다. 실행 로그의 완료 상태와 소요 시간 0.9646초를 확인했다. 데이터 준비·구현·검증 시간과 모델 학습 실행 시간을 구분하고, 화면 지표는 완료된 개발 검증 결과임을 설명했다. Grafana XY 패널의 버전 누락 때문에 자동 매핑이 빈 수동 매핑으로 변환되는 문제를 수정했다. 브라우저에서 수량·간격 두 패널의 실제 곡선이 표시되는 것까지 확인했다.

## 전체 이력 비교와 첫 최종 시험

사용자가 순서대로 진행하도록 요청했다. 2024-10-02~2026-09-15 원본 138,427행을 확보하고, 상품 식별 불명 및 연결에 영향을 받는 이력 1,148행을 격리했다. 같은 최신 스냅샷·정제 기준으로 최근/전체/최근 가중치 후보를 비교했다. 최근 후보가 전체 점수에서 유리해 동결 후 최종 시험 786건을 평가했다. [결과](../evidence/history-comparison-v1.md). 최종 시험은 사용 완료이며, 실제 앱에 연결하지 않은 미리보기 어댑터를 준비했다.

## 주기 우선으로 전환하고 모델 종류 확대

사용자는 “주기를 좀 더 중요하게 잡고 갯수 차이를 그냥 한 1개에서 2개정도 오차 범위”로 두고 여러 조건을 학습·비교하자고 요청했다. 새 모델을 받거나 학습할 수 있지만 모든 후보에 같은 시간 경계를 사용해야 하며, 이미 사용한 시험을 다시 독립 시험으로 만들 수는 없다고 설명했다.

이후 “2026년 기준 좀 최신 기술”을 질문해 공식 자료를 확인했다. 생존분석, TabPFN, 상품 추세용 Chronos/TimesFM의 역할을 설명하고 생존분석 → TabPFN 순서를 제안했다. 사용자가 “테스크대로 하나씩 진행”하도록 요청했다.

주기 우선 32구성·3구간과 생존분석 14후보·3구간을 실행했다. 재구매한 7,882건의 점수와 60일 미구매 10,248건을 분리했다. [주기 계약](../timing-experiment-v2.md), [생존분석 계약](../survival-experiment-v1.md). 날짜 회귀는 재구매가 없는 대상에도 날짜를 제시하는 약점이 드러났다. 생존분석은 추천 문턱을 높일 때 정밀도와 재현율의 교환 관계를 확인했다.

TabPFN 최신 공개 가중치는 비상업용 조건이다. 이번에는 공식 v2 가중치와 라이선스를 로컬에 보존하고 CPU 기본 한도에 맞춘 1,000개 사례 비교를 진행했다. 실행 환경에서 PyTorch 초기화 충돌이 발생해 XGBoost와 별도 프로세스로 실행하도록 수정했다. 실패 실행과 그때의 설정은 별도로 보존했고, 점수를 보기 전에 사례 수를 조정했다. 고객 데이터를 외부 API에 보내지 않는다.

비교·산출물 대사를 완료했다. [종합 결과](../evidence/timing-model-comparison-v1.md)에 전체 수치와 한계를 기록했다. 자동 테스트 57개 통과, 모든 후보의 예측과 확률 재계산, TabPFN 일부 예측 재실행·조회 불변성 점검을 확인했다. 새 Grafana 비교 화면에 표·월별 선 그래프·확률 문턱별 정밀도/재현율을 추가하고 브라우저에서 표시를 확인했다. 실제 앱이나 운영 모델은 변경하지 않았다.

## 고객군별 개별 품목 예측과 전체 이력 재비교

사용자가 기존 최근 이력 모델의 수량 ±2개와 날짜 오차를 요청해 저장 모델을 재로드했다. 기존 검증 1,196건의 수량 ±2개는 97.3%, 날짜 ±7일은 73.0%였다. 마감 뒤 재구매한 사례의 간격을 질문해 평가 포함 사례 중앙값 11일, 마감 뒤 재구매한 1,392건 중앙값 26일을 확인했다. ‘짧은 재구매’는 동일 고객×상품의 구매 사이 간격이 짧다는 설명이며, 구매 이력 길이나 고정 고객군 이름이 아님을 설명했다.

사용자가 더미 데이터 평가를 요청하고, “고객군만 묶어두고, 각 클라이언트는 따로 관리”하며 각 품목을 따로 예측한다고 구체화했다. 고객의 전체 주문일로 군을 정하고 각 고객×상품 피처는 보존하는 방식으로 구현했다. 동일 날짜의 여러 품목은 고객군용 주문일에서는 한 번 세되 품목별 구매 이력을 합치지 않는다. 11개 인공 시나리오 2,200건과 90일 관찰의 실제 역사 평가를 별도로 수행했다.

첫 270일 범위 학습 결과를 확인한 사용자는 “40퍼는 너무 낮잖아”, “전체 이력을 사용하면 안되나”라고 질문했다. 2024-10-16부터의 모든 관찰 완료 학습 사례로 범위를 확장해 동일 평가 대상에서 다시 비교했다. [고객군·전체 이력 실험](../evidence/cadence-groups-v1.md)에 결과와 평가 조건을 기록했다. 기존 73%와 새 90일 평가의 약 41%는 관찰 기간·학습 설정·평가 대상이 달라 직접 비교하지 않는다. 앱·Grafana의 기존 모델이나 화면은 변경하지 않았다.

사용자가 규칙적으로 구매하는 고객이 적은지, 한 번만 산 사례를 제외하고 반복 이력만 학습할 수 있는지 질문했다. 일반 딥러닝과 소규모 표 데이터 사전학습 모델을 구분해야 한다는 설명에 사용자는 “아니 그 TabPFN 이건 된다며”라고 지적했다. TabPFN의 소표본 적용 가능성과 한 번 구매한 개인의 미관측 주기를 아는 것은 다른 문제임을 설명하고, 반복 구매 표본에 TabPFN을 실제 적용했다. [반복 이력·TabPFN 결과](../evidence/repeat-history-v1.md)에 대상 제한과 학습 제한의 효과, 동일 1,000개 표본의 수량·주기 비교, 규칙성 진단과 검증 범위를 기록했다.
